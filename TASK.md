# НТО. Мобильная разработка. Второй тур


## Командное задание Android — «Заявки на пропуск» (35 баллов)

Организация использует электронные пропуска. Сотрудник подаёт заявку на посещение организации гостем. Охрана рассматривает заявку через служебный API. Сотрудник видит решение в мобильном приложении, обновив список или детали заявки.

Реализуйте мобильное приложение сотрудника. Выполните пять заданий: вход, список заявок, создание заявки, детали и отмена, обновление данных. Максимум — 35 баллов.

---

## 1. Общие условия

### 1.1. Проверка клиентской и серверной частей

Клиент и сервер командного задания проверяются **независимо**:

- Android-приложение проверяется с **эталонным сервером организаторов**, а не с сервером вашего напарника;
- backend проверяется отдельными API-тестами.

### 1.2. Технологии

| Область | Значение |
|---|---|
| Язык и UI | Kotlin, Jetpack Compose, Material 3 |
| Сеть | Ktor Client (движок CIO), JSON разбирается через `org.json` |
| Хранение кода входа | DataStore |
| Минимальная версия Android | API 26 |
| Сборка | Gradle 9.7.1, Android Gradle Plugin 9.4.1 (встроенный Kotlin), Compose BOM 2026.06.01, `compileSdk`/`targetSdk` 36, JDK 17 |
| Тесты | JUnit 4, Robolectric 4.17 (API 35) |
| Формат обмена | JSON, UTF-8 |
| Язык интерфейса | Русский |

Версии зафиксированы в заготовке и совпадают с окружением автопроверки. **Зависимости менять нельзя**: проверка выполняется без доступа к сети, и решение с новой библиотекой не соберётся. Navigation Compose, kotlinx.serialization и Ktor ContentNegotiation в заготовку не входят — навигация уже реализована, JSON разбирается через `org.json`.

### 1.3. Время и даты

- Все даты API имеют формат `yyyy-MM-dd'T'HH:mm:ss` без смещения: `2026-10-14T10:00:00`.
- Все значения трактуются во временной зоне `Europe/Moscow`, независимо от настроек устройства.
- Текущее время для валидации берётся **только** из предоставленного `TimeProvider` (`container.timeProvider`). В тестах время управляется организаторами.
- Форматы в интерфейсе: дата — `dd.MM.yyyy`, время — `HH:mm`, дата и время — `dd.MM.yyyy HH:mm`.

Примеры дат в задании иллюстративные. Тесты задают своё время и свои данные.

## 2. Пользовательский сценарий

1. Сотрудник входит по выданному четырёхсимвольному коду.
2. Просматривает только свои заявки.
3. Создаёт заявку на посещение гостем организации.
4. Охрана через служебный API одобряет или отклоняет заявку.
5. Сотрудник обновляет список или детали и видит новый статус.
6. Пока заявка не рассмотрена, автор может её отменить.

**Не требуются:** интерфейс охраны, сканирование камерой, регистрация устройств, периодический опрос сервера, WebSocket, push-уведомления, офлайн-редактирование, выдача QR по заявке.

### 2.1. Статусы и переходы

| Текущий статус | Действие | Кто выполняет | Новый статус |
|---|---|---|---|
| `PENDING` | Одобрение | Охрана | `APPROVED` |
| `PENDING` | Отклонение с комментарием | Охрана | `REJECTED` |
| `PENDING` | Отмена | Автор | `CANCELLED` |

Остальные переходы запрещены: сервер отвечает `409`.

| Статус | Подпись в интерфейсе |
|---|---|
| `PENDING` | На рассмотрении |
| `APPROVED` | Одобрена |
| `REJECTED` | Отклонена |
| `CANCELLED` | Отменена |

## 3. API сервера

Полный контракт — **`openapi.yaml`** в корне заготовки. Ниже — то, что нужно клиенту.

### 3.1. Вход и доступ

- Код сотрудника — ровно четыре символа: латинские буквы `A–Z`, `a–z` и цифры `0–9`. Регистр значим. Пробелы автоматически не удаляются.
- Код передаётся в пути: `/api/{code}/...`.
- Неверный формат кода — `400 {"error":"Invalid code format"}`.
- Правильный формат, но неизвестный код — `401 {"error":"Unauthorized"}`.
- Чужая заявка неотличима от отсутствующей: `404 {"error":"Request not found"}`.
- Служебный метод охраны (`PATCH /api/admin/requests/{id}` с заголовком `X-Admin-Key`) вызывают только тесты и организаторы. **Клиент его не вызывает и не содержит ключ охраны.**

### 3.2. Методы клиента

| Метод | Назначение | Успех |
|---|---|---|
| `GET /api/{code}/auth` | Проверить код | `200`, профиль |
| `GET /api/{code}/requests` | Получить свои заявки | `200`, массив |
| `GET /api/{code}/requests?status=PENDING` | Отфильтровать свои заявки | `200`, массив |
| `GET /api/{code}/requests/{id}` | Детали своей заявки | `200`, объект деталей |
| `POST /api/{code}/requests` | Создать заявку | `201`, объект деталей |
| `POST /api/{code}/requests/{id}/cancel` | Отменить свою заявку (тело не передаётся) | `200`, объект деталей |

Профиль:

```json
{"name":"Иванов Иван Иванович"}
```

Тело создания заявки:

```json
{
  "fullName": "Сидоров Пётр Ильич",
  "phone": "+79991234567",
  "organization": "ООО НТО",
  "purpose": "Встреча с сотрудником",
  "validFrom": "2026-10-14T10:00:00",
  "validTo": "2026-10-14T16:00:00"
}
```

Клиент не передаёт автора, статус, комментарий и служебные даты. Пустая организация передаётся как `null`.

Элемент списка:

```json
[
  {
    "id": 12,
    "fullName": "Сидоров Пётр Ильич",
    "validFrom": "2026-10-14T10:00:00",
    "validTo": "2026-10-14T16:00:00",
    "status": "PENDING"
  }
]
```

Список отсортирован сервером по `validFrom`, затем по `id`. Пустой результат — `[]`. Параметр `status` необязателен; допустимы только `PENDING`, `APPROVED`, `REJECTED`, `CANCELLED` в верхнем регистре.

Объект деталей (ответ деталей, создания и отмены):

```json
{
  "id": 12,
  "fullName": "Сидоров Пётр Ильич",
  "phone": "+79991234567",
  "organization": "ООО НТО",
  "purpose": "Встреча с сотрудником",
  "validFrom": "2026-10-14T10:00:00",
  "validTo": "2026-10-14T16:00:00",
  "status": "REJECTED",
  "comment": "Сотрудник отсутствует в указанный день",
  "createdAt": "2026-10-10T12:31:05",
  "updatedAt": "2026-10-10T15:02:44"
}
```

`organization` и `comment` могут быть `null`. Комментарий бывает только у отклонённой заявки.

### 3.3. Ошибки

| Ситуация | Ответ |
|---|---|
| Ошибки полей при создании | `400 {"errors": {"phone": "…", "validTo": "…"}}` — все ошибочные поля сразу |
| Дубликат заявки | `409 {"error":"Duplicate request"}` |
| Заявка отсутствует или чужая | `404 {"error":"Request not found"}` |
| Отмена не из `PENDING` (например, заявку уже рассмотрели) | `409 {"error":"Invalid status transition"}` |
| Неизвестный код | `401 {"error":"Unauthorized"}` |

Ключи `errors` совпадают с именами полей тела: `fullName`, `phone`, `organization`, `purpose`, `validFrom`, `validTo`. Ошибка формата или прошедшего времени начала приходит в `validFrom`; ошибка формата окончания и «окончание не позже начала / не в тот же день» — в `validTo`. Отдельного серверного ключа для даты нет. Текст серверных сообщений не фиксирован — клиент показывает переданный текст.

**Дубликат** — заявка того же автора с тем же телефоном в статусе `PENDING` или `APPROVED`, интервал которой пересекается с новым. Интервалы полуоткрытые: 10:00–11:00 и 11:00–12:00 не пересекаются.

### 3.4. Правила валидации

Клиент и сервер используют **одинаковые** правила. Перед проверкой длины у строковых полей удаляются начальные и конечные пробелы; отправляются нормализованные значения.

| Поле | Правило |
|---|---|
| ФИО (`fullName`) | Обязательно; 5–150 символов после обрезки пробелов |
| Телефон (`phone`) | Обязательно; `+7` и ровно 10 цифр `0–9`; крайние пробелы удаляются, пробелы и разделители внутри номера недопустимы |
| Организация (`organization`) | Необязательно; до 150 символов; пустое значение отправляется как `null` |
| Цель (`purpose`) | Обязательно; 5–200 символов после обрезки пробелов |
| Начало (`validFrom`) | Обязательно; существующие дата и время; **не раньше текущего времени** (ровно текущее время допустимо) |
| Окончание (`validTo`) | Обязательно; позже начала, в тот же календарный день |

Сервер проверяет время заново при получении запроса: если допустимое ранее время уже прошло, клиент обязан показать серверную ошибку.

### 4.2. Что реализует участник

**Весь ваш код должен лежать только в пяти каталогах** `app/src/main/java/ru/nto/guestmanagement/mobile/ui/…`. Внутри каталога — экран, его ViewModel, валидация и вспомогательные composable на ваше усмотрение. Заглушки с фиксированными сигнатурами уже лежат в заготовке.

| Каталог | Что реализовать |
|---|---|
| `ui/login/` | `LoginScreen(container, sessionExpired, onLoggedIn)` — вход |
| `ui/list/` | `RequestListScreen(container, onOpenDetails, onAddRequest, onLogout, onSessionExpired)` — список заявок |
| `ui/form/` | `RequestFormScreen(container, onBack, onCreated, onSessionExpired)` — форма новой заявки |
| `ui/details/` | `RequestDetailsScreen(container, requestId, onBack, onSessionExpired)` — детали и отмена |
| `ui/refresh/` | `ResumeEffect(onResume)` — вызывается при каждом возвращении на экран, в том числе из фона; `RefreshGate` — `launch(scope, block)` возвращает `null`, пока предыдущий запуск выполняется, `cancel()` прерывает текущее обновление |

Имена файлов, пакеты и сигнатуры менять нельзя.

### 4.3. Как каталоги проверяются

Каждый каталог проверяется **отдельно**: из вашего репозитория берётся каталог этого этапа, а остальные четыре каталога и защищённый слой подставляются эталонными. Всё, что лежит вне пяти каталогов (в том числе правки `res/`), при проверке отбрасывается. Поэтому:

- каталоги должны быть **самодостаточными**: не обращайтесь из одного каталога к классам другого. Исключение — экраны списка и деталей вызывают `ResumeEffect` и `RefreshGate` из `ui/refresh`;
- экраны списка и деталей **обязаны** использовать `ResumeEffect` и `RefreshGate`: при проверке этапа обновления ваш `ui/refresh` работает с эталонными списком и деталями, а при проверке списка и деталей — ваши экраны с эталонным `ui/refresh`;
- новые строки в `strings.xml` добавить нельзя — используйте готовые ресурсы или тексты прямо в коде;
- все пять каталогов должны компилироваться. Для невыполненного этапа оставьте компилируемую заглушку из заготовки.

## 5. Задания

Точные тексты проверяются только там, где они приведены в задании. Для остальных сообщений проверяются наличие элемента с нужным тегом и непустой текст.

### 5.1. Реализуйте вход (`ui/login/`)

1. Поле кода и кнопка `Войти`.
2. Кнопка активна только при допустимом формате кода (ровно 4 символа `A–Z`, `a–z`, `0–9`). Ввод не обрезается и не исправляется: `abcde` или `ab c` блокируют кнопку.
3. Во время запроса повторная отправка недоступна, виден индикатор; кнопка остаётся на экране, но недоступна.
4. После успешного `/auth` код сохраняется через `container.session.save(...)`, открывается список (`onLoggedIn()`).
5. После перезапуска приложения без удаления данных используется сохранённый код — экран входа пропускается, повторный запрос `/auth` не выполняется.
6. При ошибке входа (в том числе `401` на `/auth` — неверный код) показывается сообщение; оно очищается при редактировании кода или новой попытке. Текст сообщения не проверяется. После ошибки можно повторить попытку с тем же кодом.
7. Выход очищает код и возвращает на вход; после выхода поле кода пустое.
8. **`401` после входа** — на любом запросе, кроме `/auth`: приложение очищает сохранённый код (`container.session.clear()`), вызывает `onSessionExpired()` и показывает на экране входа сообщение `Сессия завершена` (`sessionExpired = true`, тег `auth_session_expired`). Это требование относится ко всем экранам.

### 5.2. Реализуйте список заявок (`ui/list/`)

1. Карточка содержит ФИО гостя, дату `dd.MM.yyyy`, интервал `10:00–16:00` и текстовый статус с цветом из ресурсов. В интервале — короткое тире `–` (U+2013) без пробелов.
2. Порядок карточек соответствует ответу API.
3. Фильтры: `Все`, `На рассмотрении`, `Одобрены`, `Отклонены`, `Отменены`. По умолчанию выбран `Все`. При выборе фильтра список запрашивается с соответствующим параметром `status`, для `Все` — без параметра. Все пять фильтров видны на экране 360 dp без прокрутки (например, `FlowRow`), а выбранный фильтр передаётся в семантику как выбранный (`FilterChip` или `selectable`).
4. Нажатие карточки открывает детали соответствующей заявки.
5. Кнопка `Новая заявка` открывает форму. Первые 4 карточки видны без прокрутки.
6. Есть ручное обновление и выход. Кнопка обновления (`requests_refresh`) видна и во время первой загрузки.
7. Для пустого результата показывается `Заявок нет`.
8. При первоначальной ошибке загрузки показываются сообщение и кнопка обновления (`requests_refresh`), по ней же выполняется повторная попытка.
9. При ошибке повторной загрузки — ручного обновления или перечитывания при возврате на экран — уже загруженный список остаётся, появляется `Нет связи`. После успешного ответа сообщение исчезает. Сообщение об ошибке и `Нет связи` никогда не показываются одновременно. При открытии экрана выполняется ровно один `GET` (`ResumeEffect` срабатывает и при первом открытии).

### 5.3. Реализуйте создание заявки (`ui/form/`)

Поля: ФИО, телефон, организация, цель, дата, время начала и время окончания.

- Дата вводится текстом в формате `ДД.ММ.ГГГГ`, время — `ЧЧ:ММ`. Подписи формата обязательны; автоматическая маска не оценивается.
- Несуществующие даты и значения времени отклоняются (`31.02.2026`, `29.02.2027`, `24:00`, `9:00`, `14.10.26` — ошибки).
- В API время отправляется с секундами `00`: `2026-10-14T10:00:00`.
- Правила валидации — раздел 3.4. «Текущее время» — `container.timeProvider`.
- Кнопка `Отправить` доступна всегда, кроме времени выполнения запроса.
- При открытии формы ошибки не показаны. Нажатие `Отправить` при некорректных данных показывает ошибки **всех** некорректных полей и не отправляет запрос. После первой попытки ошибки обновляются при редактировании полей.
- Размещение клиентских ошибок:
  - неверный формат или несуществующая дата — `form_error_date`;
  - неверный формат времени начала или начало раньше текущего времени — `form_error_validFrom`;
  - неверный формат времени окончания или окончание не позже начала — `form_error_validTo`.
- Во время отправки виден индикатор `form_loading` — отдельный элемент **вне** кнопки; кнопка `Отправить` остаётся на экране, но недоступна. Быстрые повторные нажатия не создают повторные запросы.
- Ошибки `400 errors` отображаются под соответствующими полями: `validFrom` — под временем начала, `validTo` — под временем окончания. Серверная ошибка поля исчезает при редактировании **этого** поля (правка даты ошибки `validFrom`/`validTo` не сбрасывает) и не мешает повторной отправке.
- При `409 Duplicate request` показывается общее сообщение `На это время уже есть заявка для указанного телефона`.
- При сетевой ошибке (или `5xx`) данные формы сохраняются, показывается общее сообщение и доступна повторная отправка.
- После успеха открывается список с фильтром `Все`, данные перечитываются с сервера и новая заявка видна.
- Форма прокручивается, клавиатура не закрывает доступ к полям и кнопкам: в окне edge-to-edge она приходит как IME insets, прокручиваемая область должна их учитывать (`imePadding()`). Введённые значения сохраняются при повороте экрана; сохранять незавершённую форму после закрытия приложения не требуется.

### 5.4. Реализуйте детали и отмену заявки (`ui/details/`)

1. Показать ID, ФИО, телефон, организацию (только если она задана), цель, начало и окончание, статус, время создания и изменения; все даты со временем — в формате `dd.MM.yyyy HH:mm`.
2. Для `REJECTED` показать комментарий охраны. В других статусах блок комментария отсутствует.
3. Кнопка `Отменить заявку` видна только при `PENDING`.
4. Нажатие открывает подтверждение с кнопками `Отменить заявку` и `Назад`.
5. После успешной отмены показывается статус `Отменена`, кнопка отмены исчезает; при возврате список обновляется.
6. При `409` показать `Заявка уже рассмотрена` и перечитать детали. При сетевой ошибке отмены показать сообщение; статус не меняется; после сетевой ошибки отмену можно повторить, при успехе сообщение исчезает. Сообщение `Заявка уже рассмотрена` остаётся после перечитывания и показывается вне блока кнопки отмены.
7. Есть кнопка ручного обновления деталей. При ошибке первоначальной загрузки (в том числе `404`) — сообщение и кнопка повторной попытки. При ошибке повторной загрузки последние детали остаются с сообщением `Нет связи`, которое исчезает после следующего успешного обновления. Кнопка обновления доступна и во время первой загрузки.
8. Возврат работает экранной кнопкой и системным действием «назад».

### 5.5. Реализуйте обновление данных (`ui/refresh/`)

- Онлайн-обновление не требуется: периодический опрос сервера, WebSocket и push-уведомления не реализуются и не оцениваются.
- Список и детали загружаются с сервера при открытии экрана, при возврате на экран — из деталей, формы или из фона — и по кнопке ручного обновления.
- Решение охраны, принятое при открытом экране, отображается после ручного обновления или возврата на экран.
- Пока запрос обновления выполняется, повторное нажатие не создаёт второй запрос.

## 6. Теги интерфейса

Назначьте элементам интерфейса обязательные теги из `ui/TestIds.kt` через `Modifier.testTag(...)`. Используйте точные значения, указанные в таблице: они нужны для проверки приложения.

| Экран | Обязательные теги |
|---|---|
| Вход | `auth_code`, `auth_submit`, `auth_loading`, `auth_error`, `auth_session_expired` |
| Список | `requests_filter_all`, `requests_filter_pending`, `requests_filter_approved`, `requests_filter_rejected`, `requests_filter_cancelled`, `requests_empty`, `requests_error`, `requests_offline`, `requests_refresh`, `requests_add`, `requests_logout` |
| Карточка списка | `requests_pos_{i}`, внутри — `request_name`, `request_date`, `request_time`, `request_status` |
| Форма | `form_full_name`, `form_phone`, `form_organization`, `form_purpose`, `form_date`, `form_time_from`, `form_time_to`, `form_submit`, `form_loading`, `form_error_common`, `form_back` |
| Ошибки формы | `form_error_fullName`, `form_error_phone`, `form_error_organization`, `form_error_purpose`, `form_error_date`, `form_error_validFrom`, `form_error_validTo` |
| Детали | `details_id`, `details_name`, `details_phone`, `details_organization`, `details_purpose`, `details_valid_from`, `details_valid_to`, `details_status`, `details_created_at`, `details_updated_at`, `details_comment`, `details_cancel`, `details_cancel_error`, `details_refresh`, `details_back`, `details_error`, `details_retry`, `details_offline` |
| Подтверждение отмены | `details_cancel_confirm`, `details_cancel_dismiss` |

- Все теги уже объявлены в `ui/TestIds.kt`.
- Индекс `i` начинается с нуля и соответствует позиции в текущем отфильтрованном списке.
- Вложенные теги карточек ищутся внутри контейнера карточки, поэтому карточка **не должна объединять семантику потомков** (например, `Modifier.clickable` объединяет их и скрывает вложенные теги).
- Тег назначается интерактивному элементу либо непосредственно тексту, указанному в требовании. Текст элемента деталей равен значению поля (`12`, `+79991234567`, `14.10.2026 10:00`).
- Метки статуса в карточке и деталях передают цвет через `Modifier.statusColor(...)` (или готовый `StatusLabel`).
- `form_error_common` используется для сообщения о дубликате и сетевой ошибке отправки. `details_cancel_error` — для сообщения `Заявка уже рассмотрена` и сетевой ошибки отмены.
- Ошибка поля формы — отдельный текстовый элемент со своим тегом, а не часть поля ввода.

Поля имеют видимые подписи, кнопки — понятные тексты. Контент не должен обрезаться на экране смартфона. Тесты нажимают на элементы без прокрутки, поэтому не прячьте нужные элементы за пределами экрана. Если у элемента есть прокручиваемый родитель, тест прокрутит к нему. Форма должна прокручиваться: поля находятся в прокручиваемой области. Кнопку `Отправить` можно поместить в конец этой области или закрепить внизу экрана. Кнопка `Отменить заявку` в деталях должна быть видна без прокрутки.

## 8. Проверка

- Каждое ожидание в тестах длится до 10 с. Теги ищутся в объединённом дереве семантики: элемент с тегом внутри `clickable`/`Button` может быть поглощён контейнером и не найден.
- Приложение проверяется с эталонным сервером организаторов: адрес из `Constants.HOST` подменяется.
- Тесты — Compose UI-тесты под Robolectric (экран смартфона 360×800 dp, портретная ориентация), задача `:app:testDebugUnitTest`. Эмулятор не нужен. Вёрстка в альбомной ориентации и на планшете не оценивается; поворот экрана используется только для проверки сохранения состояния.
- Каждый сценарий начинается с чистой установки. Внутри сценария допускаются перезапуск приложения, поворот экрана и переход в фон. Сохранение входа проверяется перезапуском без удаления данных.
- Скрытые тесты проверяют перечисленные требования на других данных, но не вводят новых требований. Привязывать логику к конкретным кодам сотрудников или ID заявок нельзя.

## 9. Сдача

1. Создайте **публичный** репозиторий на GitHub. Приватный репозиторий проверяющая система получить не сможет.
2. Положите проект **в корень репозитория** — так, как он лежит в заготовке (`settings.gradle.kts` в корне).
3. Отправьте ссылку на репозиторий в соответствующее задание Moodle. Pull Request создавать не нужно.
4. Проверяется **последний коммит ветки по умолчанию** на момент отправки ссылки. Изменения, отправленные позже, без повторной отправки ссылки не проверяются.
5. Submodules и Git LFS не допускаются.

После проверки результат публикуется в Moodle.
